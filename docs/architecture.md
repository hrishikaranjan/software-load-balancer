# Architecture

## 1. System architecture
```
  +--------+  +--------+  +--------+
  |Client 1|  |Client 2|  |Client N|        (bin/client, any number of threads/processes)
  +---+----+  +---+----+  +---+----+
      \          |          /
       \         | TCP :8080
        v        v         v
  +--------------------------------------------------------------+
  |                  LOAD BALANCER (1 process)                   |
  |  main thread: poll() + accept()  --fd-->  [bounded queue]    |
  |                                              |   |   |       |
  |                              worker threads  W1  W2 ... W8   |
  |  Health-checker thread ---probe---+          |   |   |       |
  |                                   v          v   v   v       |
  |                         +----------------------------+       |
  |                         |  BackendPool (mutex)       |       |
  |                         |  status, counters, router  |       |
  |                         +----------------------------+       |
  |   Statistics (atomics)            Logger (mutex + file)      |
  +-------------------------+-------------+----------------------+
                            | TCP         | TCP        | TCP
                            v             v            v
                      +-----------+ +-----------+ +-----------+
                      | Backend 1 | | Backend 2 | | Backend 3 |  separate Linux processes
                      |  :9001    | |  :9002    | |  :9003    |
                      +-----------+ +-----------+ +-----------+
```

## 2. Request data flow
1. Client opens a TCP connection to `:8080` and sends `request\n`.
2. Main thread `accept()`s -> new client fd -> `ThreadPool::submit(fd)`.
3. A worker wakes (condition variable), reads the request line (`recv_line`, 5 s timeout).
4. Worker calls `BackendPool::acquire(router)`: under the mutex the router picks a HEALTHY backend and `active_connections++`.
5. Worker `connect()`s to that backend (1 s timeout) and sends the request.
   - connect fails -> `report_forward_failure` (server marked UNHEALTHY) -> retry another healthy server.
6. Backend replies `Response generated by Backend Server N ...\n` and closes.
7. Worker calls `release(idx, ok)` (counters updated), sends the response to the client, closes the client fd.
8. Statistics and the log are updated at each step.

## 3. Health-check flow (independent of client traffic)
Every `-i` ms the health thread: `snapshot()` -> for each backend `connect()` + send `HEALTH\n` + expect `OK`
-> `report_health(idx, ok)`. Network I/O happens **outside** the mutex.

```
 UNHEALTHY --probe ok--> HEALTHY      (first start only)
 HEALTHY   --probe fails / forward fails--> UNHEALTHY
 UNHEALTHY --probe ok--> RECOVERING (1/2)
 RECOVERING--probe ok--> HEALTHY ("recovered")
 RECOVERING--probe fails--> UNHEALTHY
```
Only HEALTHY servers receive traffic; RECOVERING needs 2 consecutive good probes to avoid flapping.

## 4. Thread / process architecture
| Unit | Count | Role |
|---|---|---|
| `backend_server` processes | 3 | independent OS processes with own PID, address space, port |
| `load_balancer` process | 1 | contains all threads below |
| main thread | 1 | accept loop, signal flags, live stats |
| worker threads | 8 (`-w`) | handle one client at a time |
| health thread | 1 | periodic probing |
| admin thread | 1 | answers `STATUS`/`CHECK`/`PING` on the UNIX socket `run/lb_admin.sock` (read-only, used by the GUI) |
| backend handler threads | per connection | detached short-lived threads inside each backend |

Shared data and protection: `BackendPool` -> `std::mutex`; work queue -> `std::mutex` + `std::condition_variable`;
`Statistics` -> `std::atomic`; `Logger` -> `std::mutex`; shutdown flags -> `volatile sig_atomic_t`.
Lock order is always pool -> logger (never the reverse), so there is no deadlock.

## 5. Network architecture
All components run on loopback `127.0.0.1` (the config can point to other hosts/IPs). Ports: 8080 LB, 9001-9003 backends.
Protocol: ASCII lines over TCP. Client/LB request `text\n`; backend response `Response generated by Backend Server N (port P) | echo: text\n`;
health probe `HEALTH\n` -> `OK\n`.

## 6. Graceful shutdown order
SIGINT sets a flag -> main loop exits -> `close(listen_fd)` (no new clients) -> `ThreadPool::shutdown()` (finish queued/in-flight requests, join workers)
-> `HealthChecker::stop()` (cv notify + join) -> print/log statistics -> close log -> exit code 0.

## 7. GUI and admin channel (added later, optional)
`bin/lb_gui` is a separate process. It reads live data from the balancer over a UNIX domain socket (`run/lb_admin.sock`), reads CPU/memory from `/proc`,
starts/stops processes with `fork/exec/kill`, and sends test requests over TCP. The core data flow above is unchanged. Details: [gui.md](gui.md).
```
 bin/lb_gui ---UNIX socket---> [admin thread] --snapshot--> BackendPool / Statistics   (inside load_balancer)
     |-------/proc----------> CPU, memory, threads of every process
     |-------fork/exec/kill--> load_balancer, backend_server processes
     '-------TCP :8080 -------> normal client path
```
